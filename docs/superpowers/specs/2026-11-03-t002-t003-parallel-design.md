# T002 / T003 เป็นงานคู่ขนาน — สถานะหลัก "ส่งเอกสารฝึกสหกิจ" + สถานะรองแยกกัน

วันที่: 2026-11-03 · สถานะเอกสาร: อนุมัติแล้ว (2026-11-03)

## ทำไม

ตอนนี้ระบบบังคับลำดับ T002 → T003 ผ่านสถานะสหกิจ (`INTERNSHIP_STARTED → T002_SUBMITTED → T003_SUBMITTED → T003_APPROVED` + `*_EDITS_REQUIRED`) แต่ในงานจริงสองเอกสารนี้ **เท่ากัน** ไม่ได้ต่อกัน ผลที่เจอ:

- นักศึกษาส่ง T003 ไปก่อน T002 ถูกตรวจ → สถานะเลื่อนไปขั้น T003 แล้วตรวจ T002 ไม่ได้ (แก้ชั่วคราวด้วย "ตรวจ T002 ย้อนหลัง" ใน b0084a7 — ซับซ้อนและยังมีมุมที่แก้ไม่ได้ เช่น ตีกลับ T002 ที่อนุมัติไปแล้ว)
- นักศึกษาที่อยากส่ง T003 ก่อนส่งไม่ได้
- อนุมัติ T002 แล้วสถานะไม่เปลี่ยน (ไม่มีสถานะ "T002 ผ่าน") ป้าย/ตัวนับต้องเดาจากไฟล์

## เป้าหมาย (ผู้ใช้ตัดสินแล้ว)

1. นักศึกษาที่ออกฝึกแล้วอยู่ **สถานะหลักเดียว: "ส่งเอกสารฝึกสหกิจ"**
2. T002 และ T003 มี **สถานะรองของตัวเอง** แยกกัน: ยังไม่ส่ง / รอตรวจ / ต้องแก้ / ผ่าน
3. ส่งอันไหนก่อนก็ได้ · ตรวจ / ตีกลับ / ส่งใหม่ แต่ละอันทำแยกกัน ไม่กระทบอีกอัน
4. นัดนิเทศเดินคู่กันได้เหมือนเดิม (ไม่ต้องรอเอกสารครบ)
5. คนที่ดู: นักศึกษา (ของตัวเอง) · อาจารย์ประจำหลักสูตร · เจ้าหน้าที่ (ใครขาดอันไหน รอตรวจอันไหน)
6. นักศึกษาที่อยู่สถานะเก่า (`T002_*` / `T003_*`) ย้ายมาอยู่แบบใหม่ โดยสถานะรองมาจากไฟล์ที่ส่งไว้แล้ว

## ไม่ทำ

- ไม่เปลี่ยนขั้นก่อนหน้า (T000 / หนังสือ / ใบตอบรับ) และขั้นหลัง (นิเทศ / T005–T008)
- ไม่เปลี่ยนตัวแบบฟอร์ม T002/T003 (ฟอร์ม · บันทึกร่าง · สร้าง PDF) และกำหนดส่งของแต่ละขั้นในปฏิทินของรอบ (T002 กับ T003 ยังมีกำหนดส่งแยกกัน)
- ไม่ลบค่าเก่าออกจาก enum `CoopStatus` ในรอบนี้ (ดู "การย้ายข้อมูล")

## ห้ามเกิด (ถือว่าล้มเหลวแม้จะทำงานได้)

- นักศึกษาคนไหนหายจากหน้าตรวจ T002/T003 หรือหายจากตัวนับ ทั้งที่ยังมีไฟล์รอตรวจ
- ย้ายข้อมูลแล้วผลตรวจเดิมเพี้ยน (ผ่านกลายเป็นรอตรวจ หรือกลับกัน)
- นัดนิเทศ / ส่ง T005–T008 / ย้ายรอบ ของคนที่อยู่ช่วงฝึกงานพังเพราะสถานะเปลี่ยน
- ตีกลับอันหนึ่งแล้วอีกอันถอยหรือหาย

## แบบที่ออกแบบ

### สถานะหลัก
- ใช้ค่าเดิม `INTERNSHIP_STARTED` เป็นสถานะหลักของช่วงนี้ทั้งหมด (**การตัดสินของผม**: ไม่ต้องเพิ่มค่าใน enum ไม่ต้องมี migration ของ schema · ทุกจุดที่เช็คช่วงฝึกงานมีค่านี้อยู่แล้ว)
- ป้ายที่ผู้ใช้เห็น: **"ส่งเอกสารฝึกสหกิจ"** (แทน "ออกฝึกสหกิจ" / "กำลังฝึกสหกิจ") ทุกที่ที่แสดงสถานะหลัก
- สถานะหลักไม่เปลี่ยนเมื่อส่ง/ตรวจ T002 หรือ T003 อีกต่อไป

### สถานะรอง (คิดจากไฟล์ ไม่เพิ่มคอลัมน์)
ใช้สถานะของ `Document` ชนิด `T002_FORM` / `T003_FORM` (ไฟล์ล่าสุด) ที่มีอยู่แล้ว (**การตัดสินของผม**):

| ไฟล์ | สถานะรอง |
|---|---|
| ไม่มีไฟล์ | ยังไม่ส่ง |
| `WAITING` | รอตรวจ |
| `REJECTED` (รวม `EDITS_REQUIRED` เก่า) | ต้องแก้ |
| `APPROVED` | ผ่าน |

- ผ่านครบทั้งสอง → แสดงป้าย **"เอกสารฝึกสหกิจครบ"** (คิดจากไฟล์ ไม่ใช่สถานะใหม่) (**การตัดสินของผม**)
- ทำ helper เดียวที่ใช้ร่วมกัน: backend `utils/internshipForms.js` (`formState(doc)`, `canSubmitForm`, `canReviewForm`) และ frontend `src/utils/internshipForms.ts` ให้กติกาตรงกัน — แทน `utils/t002Review.js` / `src/utils/t002Review.ts` (ตรวจย้อนหลัง) ที่ไม่จำเป็นแล้ว

### กติกา (ใช้กับ T002 และ T003 เหมือนกันทุกข้อ)
- **ส่ง:** สถานะหลัก `INTERNSHIP_STARTED` + ไฟล์ของชนิดนั้น "ยังไม่ส่ง" หรือ "ต้องแก้" → ส่งได้ · "รอตรวจ" / "ผ่าน" → ส่งทับไม่ได้ (400) · ไม่ต้องส่ง T002 ก่อน T003 แล้ว
- **กำหนดส่ง:** ส่งครั้งแรกตามกำหนดของขั้นนั้น · ไฟล์ "ต้องแก้" = ส่งแก้ ไม่ติดกำหนด (`resolveDeadline` ดูจากไฟล์แทนสถานะ) · ป้าย "เลยกำหนด ยังไม่ส่ง" และแจ้งเตือนก่อนปิด: ทั้งสองขั้นนับคนที่อยู่ `INTERNSHIP_STARTED` และยังไม่ส่งขั้นนั้น (`FIRST_SUBMIT_STATUSES.T003` เปลี่ยนจาก `T002_SUBMITTED` เป็น `INTERNSHIP_STARTED`)
- **ตรวจ:** ไฟล์ "รอตรวจ" → อนุมัติ (ผ่าน) / ตีกลับ (ต้องแก้ + เหตุผล) · ไฟล์ "ผ่าน" → ตีกลับได้ (ข้อถัดไป) · เปลี่ยนเฉพาะสถานะไฟล์ · แจ้งเตือนนักศึกษาเหมือนเดิม (`T002_REVIEWED` / `T003_REVIEWED`) · สิทธิ์ตรวจเหมือนเดิม (เจ้าหน้าที่/อาจารย์ประจำหลักสูตร · อาจารย์ที่ปรึกษาโครงงานผ่านหน้าของอาจารย์)
- **ตีกลับอันที่ผ่านแล้ว (ผู้ใช้ตัดสิน: ได้):** ไฟล์ "ผ่าน" มีปุ่มตีกลับ (ต้องใส่เหตุผล) → กลับเป็น "ต้องแก้" นักศึกษาส่งใหม่ได้ (ส่งแก้ ไม่ติดกำหนด) · ไฟล์ "ผ่าน" ไม่มีปุ่มอนุมัติซ้ำ · "ต้องแก้" = รอนักศึกษา ตรวจไม่ได้จนกว่าจะส่งใหม่
- **ลบไฟล์:** นักศึกษาลบได้เฉพาะไฟล์ "ต้องแก้" (ส่งใหม่ทับได้อยู่แล้ว) · "รอตรวจ" / "ผ่าน" ลบไม่ได้ (409) — ทั้งทางหน้าเอกสาร และ `DELETE /api/coop/documents/:id` (ล็อกไว้แล้วตั้งแต่ 56d28d1)
- **ป้ายเมนู / จำนวนรอตรวจของรอบ:** T002 = คนที่อยู่ `INTERNSHIP_STARTED` และไฟล์ T002 "รอตรวจ" · T003 แบบเดียวกัน (แยกกัน)
- **รายชื่อในหน้าตรวจ T002/T003:** นักศึกษาที่อยู่ช่วงฝึกงาน (`INTERNSHIP_STARTED`) หรือมีไฟล์ชนิดนั้น · คอลัมน์สถานะ = สถานะรองของชนิดนั้น · ปุ่มอนุมัติ/ตีกลับขึ้นตามกติกาเดียวกับ server

### หน้าจอนักศึกษา
- หน้า T002 และหน้า T003 แยกกัน แต่ละหน้าบอกสถานะรองของตัวเอง (ยังไม่ส่ง / รอตรวจ / ต้องแก้ + เหตุผล / ผ่าน) และปุ่มส่งตามกติกา
- หน้า T003 ไม่ขึ้น "ต้องส่ง T002 ก่อน" อีก
- แถบสถานะ (`S_StatusTracker`) · เมนู (`S_Sidebar` + `utils/studentSteps.ts`) · Dashboard: สถานะหลัก "ส่งเอกสารฝึกสหกิจ" + T002/T003 ของตัวเอง · เครื่องหมายบนเมนู T002 และ T003 คิดจากไฟล์ของแต่ละอัน (ปัจจุบันทั้งสองเมนูเป็น "ขั้นปัจจุบัน" ระหว่างช่วงฝึกงาน · ผ่าน = ✓)

### หน้าจอเจ้าหน้าที่ / อาจารย์
- ตัวกรองสถานะ (`StatusFilterChips`) กลุ่มช่วงฝึกงานยังเป็นกลุ่มเดียว (สถานะหลัก)
- หน้า T000 (คนที่ผ่านขั้นหนังสือแล้ว) ป้าย "อยู่ระหว่างฝึกสหกิจ" → "ส่งเอกสารฝึกสหกิจ"
- Excel นักศึกษา: คอลัมน์สถานะ = สถานะหลัก · เพิ่มคอลัมน์ "T002" และ "T003" = สถานะรอง (**การตัดสินของผม** ถ้าทำได้ไม่ยุ่ง)

## การย้ายข้อมูล

- สคริปต์ใหม่ `backend/scripts/migrate_internship_forms.js` (`--dry-run` ก่อน แล้วค่อยจริง · รันซ้ำได้ ผลครั้งที่สองต้องเป็น 0):
  - นักศึกษาที่สถานะ `T002_SUBMITTED` / `T002_EDITS_REQUIRED` / `T003_SUBMITTED` / `T003_EDITS_REQUIRED` / `T003_APPROVED` → `INTERNSHIP_STARTED`
  - ไม่แตะสถานะไฟล์ ยกเว้นกรณีที่สถานะเก่าบอกผลตรวจที่ไฟล์ไม่มี (เช่น `T002_EDITS_REQUIRED` แต่ไฟล์ T002 ยัง `WAITING` → ตั้งเป็น `REJECTED`) — รายงานทุกกรณีแบบนี้ใน dry-run
  - รายงาน: จำนวนต่อสถานะเดิม · คนที่สถานะบอกว่าส่งแล้วแต่ไม่มีไฟล์ (ไม่แก้ แค่รายงาน)
- ค่าเก่ายังอยู่ใน enum (ไม่ลบ) เพื่อให้ถอยโค้ดกลับได้ และกันข้อมูลที่หลุดมา · โค้ดใหม่ต้องรับมือได้ถ้ายังเจอค่าเก่า (ถือว่าเป็นช่วงฝึกงาน) จนกว่าจะรันสคริปต์ · ลบออกจาก enum ได้ในรอบหลังเมื่อยืนยันว่าไม่มีข้อมูลค้าง
- Deploy: โค้ด + รันสคริปต์ dry-run → จริง บน VM (ไม่มี migration ของ schema)
